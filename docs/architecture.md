# Архитектура

Документ описывает устройство бойлерплейта: границы, слои, потоки данных
и решения, из которых всё это следует. Детали, на которых легко обжечься,
вынесены в [соглашения](conventions.md), история решений — в [ADR](adr/README.md).

## Общая картина

Приложение — модульный монолит с чётко очерченными границами внутри,
рассчитанный на то, что отдельный контекст можно будет выделить в сервис
без переписывания.

```
Браузер
   │  только свой origin, cookie с зашифрованной сессией
   ▼
Next.js (BFF)                    apps/web
   │  Bearer-токен, traceparent
   ▼
API (Laravel + Octane)           apps/api
   ├── Postgres          схема на контекст
   ├── Redis (state)     очереди, Horizon, локи, rate limits
   ├── Redis (cache)     только кэш
   └── S3                файлы
```

Браузер никогда не обращается к API напрямую: токены остаются на сервере
Next, и в браузер попадает только зашифрованный httpOnly-cookie.

## Структура репозитория

```
apps/api        API на Laravel
apps/web        Frontend на Next.js, он же BFF
packages/       Общие JS-пакеты, сгенерированный клиент API
infra/docker    Dockerfile'ы и compose-стеки
docs/           Документация и OpenAPI-спецификация
```

## Ограниченные контексты

Код контекста лежит в `apps/api/src/<Context>/`:

```
src/Identity/
├── Domain/            агрегаты, value objects, доменные события, интерфейсы репозиториев
├── Application/       сценарии (команды и запросы), порты, политики
├── Infrastructure/    реализации портов, персистентность, адаптеры
├── Presentation/      контроллеры, запросы, ресурсы, роуты
└── Contract/          публичный API контекста
```

`Shared` устроен так же и содержит только технические абстракции: базовые типы
домена, шины, транзакции, outbox, наблюдаемость. Бизнес-правила в `Shared`
не попадают никогда.

### Границы между контекстами

Контекст видит только `Shared` и `Contract` других контекстов. Внутренности
чужого контекста недоступны — это проверяет deptrac, конфигурация
в `deptrac.contexts.yaml`.

В `Contract` попадает то, что контекст обещает внешнему миру: интеграционные
события и, при необходимости, интерфейсы синхронных запросов. Всё, что там
лежит, меняется только с выпуском новой версии.

Контексты не связаны внешними ключами в базе и не джойнят чужие таблицы.
Обмен идёт через интеграционные события; при необходимости контекст держит
собственную проекцию чужих данных.

### Слои

Правило зависимостей — внутрь, проверяется в `deptrac.layers.yaml`:

| Слой | Зависит от | Не знает про |
|---|---|---|
| Domain | ничего | фреймворк, БД, HTTP |
| Application | Domain | фреймворк, БД, HTTP |
| Infrastructure | Domain, Application | — |
| Presentation | Domain, Application | Infrastructure |

Domain и Application не видят `Illuminate\*`: в домене используется
`DateTimeImmutable` и `Psr\Clock\ClockInterface`, а всё, что нужно от
фреймворка, описывается портами в Application и реализуется в Infrastructure.

Исключение — провайдеры контекстов (`Infrastructure/Provider`): это
composition root, им разрешено видеть все слои.

## Поток команды

```
HTTP-запрос
   ↓
Controller                  собирает команду, берёт Principal из запроса
   ↓
CommandBus
   ├── Authorize            проверяет право из атрибута #[RequiresPermission]
   ├── Trace                спан OpenTelemetry
   ├── Measure              гистограмма длительности
   ├── Transactional        открывает транзакцию
   └── PublishRecordedEvents
         ↓
      Handler               сценарий: загружает агрегат, вызывает метод, сохраняет
         ↓
      Repository            маппит агрегат в строки, отдаёт события коллектору
         ↓
      листенеры и трансляторы событий, запись в outbox
```

Порядок middleware — осознанное решение и закреплён тестом. Авторизация до
транзакции, чтобы отказ её не открывал. Наблюдаемость снаружи транзакции,
чтобы на спане было видно время удержания блокировок. Публикация событий
внутри неё, чтобы строки outbox коммитились вместе с агрегатом.

Команды ничего не возвращают. Идентификатор нового агрегата генерируется
до отправки команды (UUIDv7) и передаётся в неё полем.

## Чтение

Запросы идут мимо агрегатов: `QueryBus` → обработчик → read-модель на Query
Builder → DTO. Агрегаты предназначены для изменения состояния, и загружать
их ради отображения списка незачем.

Списки используют курсорную пагинацию по ключу (`KeysetPaginator`): сравнение
кортежей в Postgres и непрозрачный курсор в ответе. Offset-пагинация не
используется — она деградирует на больших таблицах и даёт дубли при вставках.

## События

Различаются два вида событий.

**Доменные** живут внутри контекста. Агрегат записывает их через
`recordThat()`, репозиторий при сохранении передаёт коллектору, middleware
шины разбирает их волнами и вызывает листенеры синхронно, в той же
транзакции. Падение листенера откатывает всю команду.

**Интеграционные** покидают контекст. Доменное событие становится
интеграционным, только если для него зарегистрирован транслятор — по
умолчанию наружу не уходит ничего.

### Transactional outbox

```
Команда (одна транзакция)
   ├── изменение агрегата
   └── строка в outbox_messages
          │ commit
          ▼
   LISTEN/NOTIFY будит relay
          ▼
   outbox:relay
   SELECT ... FOR UPDATE SKIP LOCKED
          ▼
   по одному джобу на подписчика → Redis
          ▼
   Horizon → HandleIntegrationEvent
          ├── строка в inbox_messages (идемпотентность)
          └── вызов обработчика
             всё в одной транзакции
```

Гарантия — at-least-once: relay может отправить сообщение повторно, поэтому
обработка идемпотентна за счёт inbox. Изменения в базе применяются ровно
один раз; внешние эффекты (письма, HTTP-вызовы) остаются at-least-once, и
обработчик должен это учитывать.

Битые сообщения уходят в dead letter сразу, без ретраев: ошибка данных не
исправится повторной попыткой, а в очереди такое сообщение перечитывалось бы
бесконечно. Временные сбои (недоступен Redis) не трогают счётчик попыток —
relay откатывает батч и уходит в backoff.

Подписка идёт по имени и версии события: выпуск `v2` не доставляется
обработчикам `v1` молча.

## Аутентификация и авторизация

Пользователи, токены и роли принадлежат контексту Identity. Laravel Sanctum
скрыт за портами `AccessTokenIssuer` и `AccessTokenRevoker`, поэтому переход
на JWT или внешний OIDC затрагивает только адаптеры.

**Access-токен** — opaque-токен Sanctum, живёт 15 минут.
**Refresh-токен** — собственный агрегат с ротацией: каждый одноразовый и
принадлежит «семье». Повторное использование означает утечку, и вся семья
отзывается немедленно. Исключение — короткое окно (10 секунд), в котором
повтор считается гонкой вкладок или ретраем, а не атакой.

В базе хранится только SHA-256 от refresh-токена: утечка дампа не даёт
сессий.

### Principal

Актор запроса описывается иммутабельным `Principal` (`Shared\Domain\Access`).
Он собирается один раз на границе HTTP из токена Sanctum и передаётся в
команды **явным полем**, а не через контейнер: request-scoped состояние в
singleton протекло бы между запросами в Octane.

Права токена пересекаются с правами пользователя — токен может сузить
доступ, но не расширить.

В коде приложения не используются ни `Auth::user()`, ни `Gate`, ни
`$this->authorize()`. Единственное исключение — доступ к интерфейсу Horizon,
это ops-инструмент, а не бизнес-функция.

### Два уровня проверок

Грубая проверка права — атрибут на команде, её выполняет middleware шины:

```php
#[RequiresPermission('identity.users.block')]
final readonly class BlockUser implements ActorAware, Command
```

Проверка, зависящая от состояния, живёт в домене или сценарии: «заказ можно
отменить только автору и только до отгрузки» — это метод агрегата или
доменная политика, а не право в конфиге.

Роли определяются в `config/identity.php` как наборы прав: набор прав роли —
часть логики приложения, а не пользовательские данные. Связь
«пользователь — роль» лежит в базе.

## API

Ответы — обычный JSON без обёртки. Коллекции всегда объект, а не массив
верхнего уровня, чтобы можно было добавить метаданные без ломки контракта:

```json
{ "items": [...], "page": { "nextCursor": "...", "limit": 50 } }
```

Ошибки — RFC 9457, `application/problem+json`, со стабильным машинным кодом
и идентификатором трассировки:

```json
{
  "type": "https://api.example.com/problems/identity/user-blocked",
  "title": "User is blocked",
  "status": 403,
  "code": "identity.user_blocked",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

Доменные и прикладные исключения ничего не знают про HTTP. Сопоставление
делает `ProblemMap`, который наполняет каждый контекст; поиск идёт от
точного класса к родителям, поэтому базовые `NotFound`, `AccessDenied` и
`InvalidInput` покрывают наследников автоматически.

Контракт описан вручную в `docs/api/` (spec-first). Каждый HTTP-вызов из
feature-тестов проверяется против спецификации автоматически: эндпоинт,
которого нет в спеке, или ответ, расходящийся со схемой, роняет тест.

## Frontend и BFF

Next.js выступает посредником: браузер обращается только к своему origin,
а `/bff/*` проксирует запросы в API.

Сессия — зашифрованный (JWE, A256GCM) httpOnly-cookie с обоими токенами.
Подписи было бы мало: подписанный токен читается всеми, у кого есть cookie.

Обновление токена происходит в прокси, упреждающе за минуту до истечения, с
защитой от параллельных обновлений в одном процессе. Между инстансами
эту роль играет окно грейса на стороне API.

Данные для интерфейса идут через TanStack Query, серверные компоненты
отвечают за каркас страницы и первичную проверку сессии. Мутации —
Route Handlers, а не Server Actions: их можно вызвать из любого клиента и
типизировать против OpenAPI.

## Наблюдаемость

Трассировка сквозная: запрос браузера → BFF → API → команда → outbox →
консьюмер очереди остаются одним трейсом благодаря W3C traceparent, который
передаётся в метаданных сообщения.

Метрики: длительность HTTP-запросов по шаблону роута, длительность команд,
обработка интеграционных событий, глубина очередей и — главное — возраст
самого старого неопубликованного сообщения outbox. Последняя метрика
одновременно ловит упавший relay, залипшую транзакцию и забитую очередь.

Логи структурированные, в stdout, с `trace_id` и `span_id` для связи с
трассами.

## Развёртывание

Один образ, разные роли: `web`, `horizon`, `scheduler`, `outbox-relay`,
`migrate`. Роль выбирается аргументом entrypoint, в Kubernetes это будут
отдельные Deployment'ы.

Образ рассчитан на кластер: непривилегированный пользователь, read-only
корневая файловая система, конфигурация только через переменные окружения,
корректное завершение по SIGTERM, health-эндпоинты для проб.

Миграции выполняются отдельной задачей, а не при старте контейнера: иначе
несколько реплик устроили бы гонку.

Кэш конфигурации (`config:cache`) не создаётся при сборке — он запёк бы
значения переменных времени сборки. Кэши маршрутов и событий создаются,
они от окружения не зависят.
