# 0006. Next.js как BFF, токены не попадают в браузер

- Статус: Принято
- Дата: 2026-09-26

## Контекст

Фронтенд должен работать с API, у которого одноразовые refresh-токены с
ротацией и детекцией повторного использования. Хранение токенов в браузере
означает их доступность любому скрипту на странице.

Отдельная сложность: в Next.js cookie нельзя установить во время рендера
серверного компонента. Если несколько компонентов страницы параллельно
обнаружат истёкший токен, каждый попытается обновить сессию одним и тем же
refresh-токеном — для API это выглядит как утечка, и вся сессия отзывается.

## Решение

Браузер обращается только к своему origin. Маршрут `/bff/*` проксирует
запросы в API, подставляя access-токен. Сессия хранится в зашифрованном
(JWE, A256GCM) httpOnly-cookie.

Обновление токена происходит в прокси, упреждающе за минуту до истечения, с
single-flight: параллельные запросы в одном процессе ждут один результат.

Мутации выполняются через Route Handlers, а не Server Actions.

## Альтернативы

**Токен в localStorage и прямые запросы к API.** Проще, но токен доступен
любому скрипту, и ротация требует синхронизации между вкладками.

**Sanctum в cookie-режиме (stateful SPA).** Требует общего домена и делает
API stateful.

**Server Actions для мутаций.** Завязаны на React-транспорт: их нельзя
вызвать из мобильного клиента, сложнее типизировать против OpenAPI и
отлаживать.

## Последствия

- API остаётся полностью stateless и не знает про cookie.
- Дополнительный сетевой переход добавляет задержку.
- Single-flight работает в пределах процесса; между инстансами Next нужен
  грейс-период на стороне API ([ADR 0012](0012-refresh-grace-window.md)).
- Адрес API не попадает в браузерный бандл.
