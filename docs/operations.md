# Эксплуатация

## Образы

Один образ содержит приложение целиком, роль выбирается аргументом:

| Роль | Команда | Назначение |
|---|---|---|
| `web` | по умолчанию | HTTP-сервер Octane |
| `horizon` | | обработчики очередей |
| `scheduler` | | планировщик |
| `outbox-relay` | | публикация интеграционных событий |
| `migrate` | | применение миграций, завершается после выполнения |
| `artisan` | | произвольная команда |

```bash
docker run --rm ghcr.io/kalitvyan/laravel-boilerplate-api:latest artisan about
```

Образы собираются в CI при пуше в `master` и по тегам `v*`, публикуются в
GHCR: `laravel-boilerplate-api` и `laravel-boilerplate-web`.

Локальная сборка:

```bash
make prod-images                              # оба образа
make prod-image REGISTRY=ghcr.io/kalitvyan    # с тегом реестра
```

## Свойства образа

- Непривилегированный пользователь (UID 10001).
- Read-only корневая файловая система; запись только в `/tmp`,
  `storage` и `bootstrap/cache`, которые монтируются отдельно.
- Конфигурация только через переменные окружения.
- Корректное завершение по SIGTERM во всех ролях.
- Кэши маршрутов и событий созданы при сборке; кэш конфигурации — нет,
  он запёк бы значения времени сборки.

В Kubernetes потребуется `securityContext` с `runAsUser`, `runAsGroup` и
обязательно `fsGroup`: без него процесс не сможет писать в примонтированные
тома.

## Переменные окружения

### Обязательные

| Переменная | Назначение |
|---|---|
| `APP_KEY` | ключ шифрования Laravel |
| `DB_*` | подключение к PostgreSQL |
| `REDIS_HOST` | инстанс для очередей, локов и rate limits |
| `REDIS_CACHE_HOST` | инстанс для кэша |
| `AWS_*` | доступ к S3-совместимому хранилищу |

Для фронтенда: `API_URL` и `SESSION_SECRET` длиной не менее 32 символов.

### Существенные для поведения

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `OCTANE_WORKERS` | 4 | задаётся числом; автоопределение увидит CPU узла, а не лимит пода |
| `OCTANE_MAX_REQUESTS` | 500 | перезапуск воркера, страховка от утечек |
| `IDENTITY_ACCESS_TTL` | PT15M | время жизни access-токена |
| `IDENTITY_REFRESH_TTL` | P30D | время жизни refresh-токена |
| `IDENTITY_REFRESH_GRACE` | 10 | окно, в котором повтор считается гонкой |
| `TRUSTED_PROXIES` | приватные сети | никогда не `*`, если API доступен из интернета |
| `API_RATE_LIMIT_PER_MINUTE` | 120 | общий лимит запросов |
| `OTEL_ENABLED` | false | трассировка |
| `OTEL_METRICS_ENABLED` | false | метрики |

## Два инстанса Redis

Разделение обязательно и не является оптимизацией.

**Кэш** работает с политикой `allkeys-lru` и без персистентности.
**Состояние** — очереди, Horizon, локи, счётчики rate limit — требует
`noeviction` и AOF.

Политика вытеснения задаётся на инстанс, а не на базу внутри него. Если
объединить, под нагрузкой Redis может вытеснить лок, и `WithoutOverlapping`
или `onOneServer()` молча перестанут работать.

## Миграции

Выполняются отдельной задачей до обновления приложения:

```bash
docker run --rm --env-file .env ghcr.io/kalitvyan/laravel-boilerplate-api:latest migrate
```

Используется флаг `--isolated`: несколько реплик не выполнят миграции
одновременно.

## Наблюдаемость

### Что отслеживать

| Метрика | Смысл |
|---|---|
| `app_outbox_lag_seconds` | возраст самого старого неопубликованного события |
| `app_outbox_dead_lettered` | сообщения, требующие ручного разбора |
| `http_server_request_duration_seconds` | RED-метрики по шаблонам роутов |
| `app_command_duration_seconds` | длительность сценариев |
| `messaging_process_duration_seconds` | обработка интеграционных событий |
| `app_queue_depth` | глубина очередей |

Лаг outbox — главный индикатор здоровья: он одновременно ловит упавший
relay, залипшую транзакцию и переполненную очередь.

Гейджи снимает команда `telemetry:collect`, запускаемая планировщиком раз в
минуту.

### Примеры запросов

```promql
# Доля ошибок
sum(rate(http_server_request_duration_seconds_count{http_response_status_code=~"5.."}[5m]))
  / sum(rate(http_server_request_duration_seconds_count[5m]))

# p95 по роутам
histogram_quantile(0.95, sum by (le, http_route) (rate(http_server_request_duration_seconds_bucket[5m])))

# Лаг публикации событий
max(app_outbox_lag_seconds)
```

Стартовый набор правил оповещения — в `infra/observability/alerts.yaml`.

## Разбор инцидентов

**События не доходят до потребителей.** Проверьте `app_outbox_lag_seconds` и
работу процесса relay. Если лаг растёт, а relay жив — посмотрите
`last_error` в таблице `outbox_messages`. Сообщения со счётчиком попыток,
достигшим предела, в dead letter и требуют ручного вмешательства.

**Пользователей разлогинивает.** Посмотрите в логах записи об отзыве семьи
токенов. Частые срабатывания при нормальной работе означают, что окна грейса
не хватает: увеличьте `IDENTITY_REFRESH_GRACE`.

**Очередь растёт.** Проверьте число процессов Horizon и наличие упавших
джобов (`queue:failed`). Масштабировать следует числом подов, а не процессов
внутри пода.

**Медленные ответы.** Найдите трассу по `X-Request-Id` из ответа: в ней
видно, где потрачено время — в команде, в транзакции или во внешнем вызове.

## Резервное копирование

Состояние живёт в трёх местах:

- PostgreSQL — основные данные, включая outbox и inbox;
- Redis (state) — очереди в процессе обработки; потеря означает переотправку,
  что безопасно благодаря inbox;
- S3 — файлы.

Redis-кэш восстановления не требует.

## Подключение наблюдаемости в проде

Приложение отправляет трассы и метрики по OTLP через HTTP+JSON. Своего
коллектора оно не поднимает и не требует — достаточно указать адрес:

```dotenv
OTEL_ENABLED=true
OTEL_METRICS_ENABLED=true
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318
OTEL_SERVICE_NAME=laravel-boilerplate-api
OTEL_SERVICE_VERSION=<тег образа>
OTEL_TRACES_SAMPLER_ARG=0.1
```

`OTEL_TRACES_SAMPLER_ARG` под нагрузкой обязательно снижается: при значении
1.0 каждый запрос порождает трассу, и хранилище растёт быстро. Решение о
сэмплировании принимается на корне трассы и наследуется вложенными спанами,
поэтому цепочка запрос → команда → консьюмер не рвётся.

### Варианты приёмника

**Собственный OpenTelemetry Collector** в кластере, за ним — Tempo, Prometheus
и Loki. Коллектор снимает с приложения заботу о ретраях и буферизации и
позволяет менять бэкенд, не трогая приложение.

**Управляемый сервис.** Grafana Cloud и большинство облачных провайдеров
принимают OTLP напрямую, обычно требуя заголовок с ключом. Тогда понадобится
`OTEL_EXPORTER_OTLP_HEADERS`.

### Что учесть

Метрики экспортируются с cumulative temporality. Prometheus принимает такие
точки нативно; приёмники, ожидающие delta, потребуют конвертации в
коллекторе — см. [ADR 0010](adr/0010-otlp-cumulative-temporality.md).

Дашборд из `infra/observability/grafana/dashboards/api.json` переносится в
любую инсталляцию Grafana импортом: Dashboards → New → Import → Upload JSON.
Он рассчитан на источник данных Prometheus и не содержит привязки к
конкретному окружению.

Правила оповещения — в `infra/observability/alerts.yaml`, формат Prometheus.
Пороги в них стартовые и подбираются под реальный трафик.

## Производительность

### Методика

Замеры выполняются против prod-подобного стека (`make prod-up`) с
отключённой телеметрией: экспорт трасс и метрик сам по себе добавляет
накладные расходы.

```bash
LABEL=baseline make load
```

Скрипт `infra/load/run.sh` прогревает приложение и снимает три сценария:
пустой эндпоинт, чтение с аутентификацией и то же чтение через BFF.
Результаты складываются в `infra/load/results/<label>/` и сравниваются
между запусками.

Запись измеряется отдельно (`infra/load/write.sh`), потому что требует
уникальных данных в каждом запросе. На время замера нужно поднять
`API_RATE_LIMIT_PER_MINUTE`, иначе тест упрётся в троттлинг.

### Ориентиры

Измерено на ноутбуке, где Docker располагает четырьмя ядрами и на них же
работают база, Redis и вся обвязка. Абсолютные значения справедливы только
для этой конфигурации; полезны соотношения.

| Сценарий | Пропускная способность | p50 |
|---|---|---|
| Пустой эндпоинт | 3350 rps | 14 мс |
| Чтение с аутентификацией | 390 rps | 126 мс |
| То же через BFF | 284 rps | — |
| Регистрация | 17 rps | — |

Обработка одного запроса `GET /api/v1/users/me` вне нагрузки занимает 17 мс,
из них на базу приходится около 1.4 мс при четырёх запросах. Остальное —
работа PHP. Под нагрузкой p50 растёт до 126 мс: это ожидание в очереди, а не
замедление обработки.

Регистрация упирается в bcrypt и медленная намеренно: это защита от подбора,
а не узкое место, требующее оптимизации.

### Подбор числа воркеров

`OCTANE_WORKERS` задаётся числом и подбирается под лимит CPU пода. Ориентир —
примерно по воркеру на ядро: нагрузка здесь преимущественно
процессорная, а не ожидание ввода-вывода.

Измерения на четырёх ядрах: 2 воркера — 257 rps, 8 воркеров — 390 rps,
24 воркера — 330 rps. Превышение оптимума ухудшает результат за счёт
переключения контекста.

Помните про соединения к базе: каждый воркер держит своё. При числе
воркеров, умноженном на число подов, приближающемся к `max_connections`
Postgres, нужен пул соединений.

### Где искать причину замедления

Сначала определите, ждёт запрос или работает. Сравните длительность
корневого спана в Tempo с p50 из нагрузочного теста: большой разрыв означает
очередь, то есть нехватку воркеров или подов, а не проблему в коде.

Количество и длительность запросов к базе на один вызов:

```bash
docker compose -f infra/docker/compose/compose.prod.yaml exec postgres \
  psql -U app -d app -c "ALTER SYSTEM SET log_min_duration_statement = 0;"
docker compose -f infra/docker/compose/compose.prod.yaml exec postgres \
  psql -U app -d app -c "SELECT pg_reload_conf();"
```

Обратите внимание: `log_statement = 'all'` не покажет запросы, выполненные
через prepared statements, а PDO использует именно их. Нужен
`log_min_duration_statement`.

После замера логирование обязательно выключается
(`log_min_duration_statement = -1`).
